# 晴雪湾两端扶运：几何与控制可实施性

2026-09-13。下一阶段方案，**没有新增雪湾生产代码、运行图形或真人试玩**。本次只运行忽略目录中的 `.cache/snow-geometry-probe.mjs`：`node .cache/snow-geometry-probe.mjs` 退出 0。它是独立数学探针，不属于正式游戏测试；克隆仓库不会取得忽略文件。本文保留足够坐标和规则以重建探针。

结论：固定盘体、自由前端与沿线尾端可以共同通过 S 弯；但不能直接采用[原草案](snow-prototype-review.md)的石旁中心线，也不能只给现有小暖跟随代码增加一个速度上限。

## 1. 可通过，也确实会碰内弯

保持世界 2300×1650、猫体径半径 12、刚性雪盘 100×70、冰道宽 220。两猫之间连接的是短绳把手，允许 **144–176px**，盘体始终 100×70，不随握距缩放。盘体中心取两猫中点，长轴取尾猫指向前猫的单位向量。

原草案在 A 石旁的 `(1350,770)→(1510,770)` 有实际冲突：两猫都安全、握距 160，但盘体范围 `x1380–1480/y735–805` 与石 A `x1390–1540/y660–745` 重叠 10px。原 y770 不能作为默认扶运线。

建议尾端可见路线使用以下控制点，转角两侧各截去 60px，以原顶点为控制点做二次曲线；短边截距不超过边长的 40%。绘画与碰撞共同使用细分后折线，最大采样段长 2px，禁止美术另画一条更圆的路线。

```text
(964,1155) → (1130,920) → (1320,810) → (1500,810)
→ (1650,860) → (1790,740) → (1920,600) → (2020,500)
```

保留石 A `{1390,660,150,85}`、石 B `{1730,880,115,90}`；中站垫 `(1010,1090),r180`、弯中垫 `(1530,810),r125`、邮台垫 `(1990,530),r170`。末路点改为 `(2020,500)`：若前猫停在垫中心，尾猫仍距中心约 160，加 12px 体径会超出 r170；向垫内继续 42px 后两猫及全盘都能入垫。

令细分路线的弧长参数为 `γ(s)`。一条参考解是尾猫 `γ(s)`、前猫 `γ(s+160)`；**这仅是用来证明可解的参考轨迹，不能拿来自动移动前猫**。

| 探针实际检查 | 结果 |
| --- | --- |
| 路线长度 / 路点 | 1346.25px / 688 点 |
| 连续参考姿态 | 595 个；相邻尾端进度约 2px |
| 参考握距 | 148.14–160.00px，处于 144–176 范围 |
| 整盘保守地面余量 | 最小 21.82px；不是只测四角 |
| 起始姿态 | 尾 `(964,1155)`、前 `(1056.31,1024.32)`，全盘及两猫在中站垫内 |
| 终点姿态 | 尾 `(1907.52,613.79)`、前 `(2020,500)`，全盘及两猫在邮台垫内 |
| 停步 / 横向往返 / 反向 | 10000 次零位移调用尾端零推进；直线横移往返不推进；前进 80px 后退 80px 回到原进度 |

错误内弯也经过**相同有符号投影驱动尾端**的探针验证：前猫从 `(1497.09,814.40)` 向北小步走，到候选 `(1497.09,768.40)` 时，尾猫为 `(1331.20,815.27)`，握距 172.38，两猫脚下安全，盘体却碰石 A。上一合法姿态前 `(1497.09,770.40)`、尾 `(1331.68,815.16)` 可以停住，原路逐步退回；参考轨迹另验证了 80px 的反向全盘扫掠。碰石不需要先破坏握距，不是“绳子太短”伪装出的转弯题。

验证方法：盘体用完整凸矩形 SAT 对石块；地面用盘体外接圆半径 `sqrt(50²+35²)=61.03` 包住整个盘体，确认该圆完全位于某个冰道胶囊或垫子内。这比测四角保守。对相邻姿态，以端点位移及单位长轴变化计算所有盘角的最大位移界；起始形状与按该界扩大的石块不相交、地面余量大于该界，才认证整个时间区间。无法认证则二分检查，仍不确定则拒绝。最终运行包含 684 个已认证区间，最大细分深度 2；因此不是只凭 595 张离散姿态声称中间安全。生产实现仍须复核精度和性能。

## 2. 尾端如何由前猫驱动

存两个运行时游标：前端局部投影 `frontS`、尾端已实际走到的 `tailS`。玩家前猫保留真实二维位置，不吸附到路线。一次候选前端移动得到局部投影变化 `ds = newFrontS - frontS`，候选尾端为 `γ(tailS + ds)`。

- **不累计正距离，不存待偿还位移，不按时间推游标。** 前猫实际零位移时不重算出推进；`ds<0` 允许尾端沿已走路线后退。左右绕回不能变成进度奖励。
- 投影只在当前游标附近、按本次最大合法步长能到达的连续路段内寻找。细分折线可能跨多个 2px 小段，不能全路找最近点，也不能把搜索机械限定为两个小段。
- 两端位移分别受 `135px/s × 有效 delta` 约束；有效 delta 为 `0–50ms`，非法值拒绝推进。前端侧移若使尾端投影变化过快，缩短本次**共同**接受的移动比例，不留下以后自动补走的欠账。
- 两猫与盘体扫掠、144–176 握距、运输地面必须同时成立，才共同提交。遇阻只接受到首次接触前的合法比例，随后清惯性；下一帧允许反向。不要把前猫拉回路线，也不要让尾端先走完再瞬移纠正。
- `update/observe(0)` 只核对实际到位、读取当前姿态，不推进游标或停靠节点。暂停不调用推进。只有实际入垫、低速、玩家另按 F 才发一次停靠事件。

松开按键仍可能存在冰惯性，这属于前猫的真实移动，尾端可以同速跟随；禁止的是“猫已经停住，尾端还按定时器前进”。反向输入先刹车，真正倒退后 `ds` 才变负。

## 3. 建议纯模型接口

建议 `SnowEscort` 不依赖 Phaser、Journey 或存储。以下均为待实施接口；状态与返回值深只读。

```ts
type Checkpoint = 'start' | 'sunBench' | 'mailDeck';
type Phase = 'laid' | 'awaitingEcho' | 'holding' | 'matchedPendingSave' | 'complete';
new SnowEscort(checkpoint?: Checkpoint);
assign(player: Point): Action; // 近场；返回去当前真实尾把手的可见路线
observe(sample: { player: Point; echo: Point; echoStays: boolean }): Event[];
grip(player: Point): Action;   // 最近实际 sample、前把手近场、小暖真的到位
planStep(input: { deltaMs: number; desiredFront: Point }): StepPlan;
commitStep(planId: number, actual: { player: Point; echo: Point }): Event[];
release(): Action;            // 原地放稳，保留当前位置和运行时游标
cancel(): Action;             // 先放稳，返回仅包含尾端已走部分的回程路线
dock(player: Point, actualSpeed: number): Action;
confirmSaved(stop: 'sunBench' | 'mailDeck'): Action;
stopMotion(): void;           // 清速度与未提交 plan，不改已确认节点
getSnapshot(): Snapshot;
```

`StepPlan` 至少包含单调序号、`acceptedPlayer/acceptedEcho`、盘体四点、真实速度、`blockedReason`，零位移也可成功。`planStep` 不改进度；提交后核对两只真实实体与计划位置一致，过期、重复 plan 或任一端未按计划移动都不能推进。`Snapshot` 至少暴露 phase、当前站、两把手、盘体、frontS/tailS、已走尾端路线、握距、下一可见路段、当前阻挡、已确认站与 pending。

错误码保持可解释：`not-assigned / echo-not-ready / far-from-grip / invalid-sample / stale-plan / span-limit / body-blocked / outside-ice / not-docked / moving-too-fast / awaiting-save`。大幅外部位移进入一次明确的安全垫恢复，不把异常坐标当合法下一步。

停靠匹配时立即放稳并冻结物件位置，再等保存确认，避免沙原曾发现的“待保存时物件仍跟着走远角色”问题。重试只确认原事件。恢复只从已确认固定站姿态开始，不保存浮点游标或任意冰上坐标。

## 4. PostalWalkScene 最小接入边界

现有 [update](../src/scenes/PostalWalkScene.ts) 先处理 E/F，再设猫速度、移动小暖、更新动画，最后才调 `tickJourney`。本仓库安装的 Phaser `Systems.step` 还会在场景 `update` 前发 `UPDATE`，Arcade World 在该事件更新物理，随后 `POST_UPDATE` 把物理位移提交到 Sprite。**不能在 tickJourney 末尾才做整盘约束；只限制小暖的正向步长也不能处理尾端后退。**

建议保留旧场景默认路径，只增加这些有限接点：

| 接点 | 责任 |
| --- | --- |
| `canStartDash()`，默认 true | 在设置冲刺计时、声音、动画之前拒绝扶运轻跃 |
| `onWalkControlsCleared(reason)`，默认空 | 暂停/失焦/恢复/退出清冰惯性和未提交 plan；不把“清输入”误作重置已确认节点 |
| 现有速度钩子增加只读输入上下文 | 原始方向、点击目标、剩余距离；点地刹停采用 `v²/(2a)`，不只给归一化方向 |
| `stepCoupledWalk(context): result \| null`，默认 null | 扶运时共同计划、验扫掠、提交两猫一次，再用真实提交速度驱动动画；跳过基类这帧的普通猫/echo 移动 |
| `recallEcho(route?)` 的可选实际回程 | 只用当前尾端已走路线反向接玩家脚印；不能走未访问路点或直接跨石追猫 |

扶运接管期间将猫 `body.moves=false` 并清旧速度，以合法计划位置调用一次 `body.reset` 同步实体与物理体；这属于正常运动提交，不是碰撞后回跳。释放时同步当前位置、清惯性再恢复 `moves=true`。不要让 Arcade 与手动提交同时推动同一猫。真正取消分工前先取得模型回程；每帧不能用 `sendEchoRoute` 重置队列。

普通空手冰行仍可使用既有速度路径。必要回归应覆盖拿起/放下所在帧的 Arcade UPDATE/POST_UPDATE、暂停首帧与重进，证明没有双重位移；纯模型探针不能替代这些真实顺序测试。

## 5. 实施前仍须守住的边界

1. 本次只证明第二段 S 弯及两端停靠姿态。第一段、中站两段之间**同一雪盘如何原地换朝向**、干路接口、箱盖路线、世界全部可达性尚未验证。建议中站只旋转现有雪盘至第二段安全姿态，提供清楚的原地摆盘动作；不要刷新出第二个盘子或在保存时静默传送两猫。
2. 碰石应拒绝共同候选并清速度，允许后退；不应每次轻碰都退回整段起点。非法地面救援才使用最近实际踏稳垫，并同步两猫、盘子和两种游标。碰石后松手、召回、重新到两把手必须仍有安全步行路径。
3. 最窄参考握距距下限约 4.14px，须在 30/60/120Hz、有侧向偏移和长帧下检查部分接受策略。探针中的 0.25px 局部投影搜索只用于验证，生产宜用连续段投影，避免细小量化抖动。
4. 两端到垫、全盘在垫、速度低、F 与真实回执分别判定；前端绕干路先到、远段投影、站着等待、重复 E/F 都不替代尾端实际运输。存储沿用[雪湾评审](snow-prototype-review.md)的两节点、未来版本保护和待保存重试约束。

原型加回邮局的 10–15 分钟仍是制作预算。参考尾端实际路程约 1186px，按 135px/s 算出的纯匀速位移下限仅约 8.8 秒；它清楚表明不能靠这条路线或文字量宣称已有对应体验时长，更不能据此宣称三小时成品。下一步先做完整控制切片，再用不看源码的实际玩家验证读路、错误恢复、两端协作与结局节奏。
