# rc.3 存档失败恢复设计

本文说明 1.3.0-rc.3 对本地存档失败的处理契约，供后续维护和回归检查使用。它记录实现与本轮分项测试结果；最终发布状态、完整测试总数和浏览器验收以[发行准备与验收](release-readiness.md)为准。

## 本轮解决的问题

原来的战役结算先保存路线，再保存暖晶与成长。若第 3、8 或 15 关的路线写入成功，而成长写入失败，玩家仍能继续下一关。离开结算后没有持久补偿入口，已通关路线与角色解锁可能长期不一致。最近完成记录还有 100 条窗口，不能单独承担待发奖励的保存责任。

影子切磋允许独立选择五档挑战，旧奖励却按“最高档及其之前所有档位”计算。先赢第 5 档会提前领取低档奖励，随后首次赢第 1 档时，切磋纪录显示首胜，钱包却没有对应首胜奖励。另一些结算失败只保留了显示数据，没有保留可以原样重试的完整输入；习惯日记也可能在保存失败时被描述为已保存。

路线读取遇到未知未来版本时曾退回默认视图，后续通关写入可能用当前版本覆盖原始数据。本轮把“能显示降级视图”和“有权写回存档”分开判断。

## 战役：先保存待发凭据，再发奖，再确认

[CampaignProgressionManager](../src/systems/CampaignProgressionManager.ts) 继续使用 `shadowlegion_campaign_v1`，领域版本仍为 `1`，增加 `pendingRewards: StageReceipt[]`。每张凭据保存原始完成 ID、关卡、角色、星数和胜负。只有合法且与路线通关记录相符的胜利凭据进入待发队列。

一次战役结算按以下顺序执行：

1. 校验当前存档是否可写、关卡是否开放、完成输入是否合法，以及同一 ID 是否属于同一场结果。
2. 把路线记录、最近完成凭据和新的待发凭据写入同一个 Campaign JSON。写入后立即读回，完整字符串一致才确认 `routeSaved: true`。未经这一步确认，不调用钱包发奖。
3. 按先进先出顺序调用 `MetaProgressionManager.recordStageProgress`，始终使用原始凭据 ID。遇到第一个 `saved: false` 就停止，保留该项及之后的项。这也避免后到的高星结果先于旧的低星结果处理。
4. 仅对钱包确认保存的连续前缀执行队列确认（ack）：移除这些项，再写回并读回 Campaign。确认失败时不宣称队列已经处理完；后续仍可用同一凭据重试。

路线和待发凭据在同一条存储记录中提交，钱包是另一条记录。这是带幂等补偿的分步提交，不是跨多个 `localStorage` 键的数据库事务，也不提供多个标签页同时写入时的串行化保证。

| 返回状态 | 可确认的事实 | 调用方应如何处理 |
| --- | --- | --- |
| `routeSaved: false` | 本次路线及凭据尚未通过落盘读回确认 | 保留当前页完整输入并允许重试；不能承诺刷新后自动找回 |
| `routeSaved: true, saved: false` | 本次结果已有持久恢复依据；钱包或队列确认仍未完成 | 可以离开后补偿；还需单独检查习惯日记等仅在内存的结果 |
| `routeSaved: true, saved: true` | 路线已确认，待发队列已处理并确认清空 | 可按正常完成结果继续 |

`saved: false` 不等于“没有到账”。钱包可能已经成功写入，只是后续队列确认失败；此时 `earned` 可以大于零。`total` 表示实际读到的钱包余额。`recordStageResult` 的 `earned`、`masteryXp` 对应当前凭据，`unlocks` 还可能包含本次顺带补发的更早凭据所触发的解锁。

钱包凭据去重与逐关已付记录使队列确认失败后的重试不会重复发放。若一次写入实际完成、只是读回失败，调用方仍按未确认处理，之后通过持久凭据识别已完成的部分；不能把一次接口失败解释为所有存储都未变化。

### 刷新恢复与队列上限

`reconcilePendingRewards()` 返回 `{ saved, pending, earned, total, masteryXp, unlocks }`，金额和经验为本次补偿合计。[菜单](../src/scenes/MenuScene.ts)、[路线](../src/scenes/CampaignScene.ts)、[工坊](../src/scenes/WorkshopScene.ts)和[编队](../src/scenes/LoadoutScene.ts)入口在读取角色成长前调用它。刷新或重复进入这些入口可以继续补偿，不要求玩家重打一遍关卡。

`recentCompletions` 仍只保留最近 100 条；`pendingRewards` 独立保存，不因这个窗口滚动而丢失。新胜利入队上限为 256 条。达到上限时拒绝需要新增待发项的结果，返回 `pending-reward-capacity` 和 `routeSaved: false`，保留已有队列及当前页输入；不会静默淘汰最早未付项。已有凭据的重试和队列补偿仍可执行。总路线 JSON 也受原有 100000 字符限制。

### 旧 rc.2 可以确认的补偿范围

只有旧记录缺少 `pendingRewards` 字段时，才从仍保留的真实胜利凭据重建候选队列。需要满足路线星数能够支持该凭据，并且 Meta 中存在以下至少一项缺口：该关进度缺失、该关星数不足，或该角色在该关的熟练度星数不足。Meta 的全局奖励凭据或逐关 `rewardIds` 已确认领取时，不再补发。恢复出的队列必须先写入并读回 Campaign，之后才接触钱包。

已经覆盖全部星数与角色熟练度的旧结果，即使全局凭据已滚出窗口，也不推测还有一笔重玩奖励应发。旧版已经丢失的完成凭据，以及无法从现有记录区分“已付”与“未付”的纯重玩奖励，不在自动补偿范围。旧章节迁移仍只恢复合法的一星路线访问，不伪造三星或追发并不存在的首通凭据。

## 影子切磋：逐档已付账本

[MetaProgressionManager](../src/systems/MetaProgressionManager.ts) 在 Meta v3 中增加 `modeProgress.shadowRewardLedger`，账本自身版本为 `1`：

- `paidTiers` 记录已支付暖晶的具体档位，五档分别判定。
- `masteryPaidTiers[operativeId]` 记录各角色已领取熟练度的具体档位。

首次领取第 `tier` 档的暖晶为 `4 + tier * 2`，该角色首次领取该档熟练度为 `10 + tier * 2`，仍受既有总量上限约束。例如新存档先赢第 5 档，再赢第 1 档，两次分别对应 14、6 暖晶与 20、12 熟练度。最高档记录继续用于展示，不再代替具体档位的已付集合。重复完成同档不会再获得该档首胜暖晶；另一角色仍按自己的熟练度账本判断。

旧存档没有账本时，原算法已支付过最高档之前的连续档位，因此按旧 `shadowBestTier` 把 `1…最高档` 标记为暖晶已付，并按各角色旧 `shadowMasteryTiers` 建立其熟练度已付前缀。迁移本身不加钱、不扣钱、不增加经验。已有 v1 账本时，以实际档位集合为准，不能再次用最高档扩展集合，否则会重新制造跳档领取问题。

## 结算页：重试原结果，区分持久队列与内存结果

[ArenaScene](../src/scenes/ArenaScene.ts) 将原始结算输入传给 [GameOverScene](../src/scenes/GameOverScene.ts)。重试保存回信的按钮和 `S` 使用同一场结果，刷新的是结算页面，不是重新进行战斗。保存未完成时，`R` 也先走保存重试，下一关按钮不会绕过待处理结果。

| 结果领域 | 结算页保留的输入 | 重试与完成判断 |
| --- | --- | --- |
| 战役路线及成长 | 完整 `StageCompletion`，包含原始 `completionId`、角色、时长、营地/生命比例和任务指标 | 再次调用同关 `recordStageResult`；已完成部分按原凭据去重 |
| 影子切磋纪录与钱包 | 原始 `completionId`、档位、时长、角色 | 分别重试失败的 `recordVictory` 或 `recordModeProgress`；两者的保存状态独立显示 |
| 习惯日记及局统计 | 原始 `RunSummary`，包含原始档案、模式和完成 ID | 以同一 summary 调用 `recordRun`，通过持久 `run:<completionId>` 凭据确认；失败局也保留这份输入 |

[ShadowTrialManager](../src/systems/ShadowTrialManager.ts) 每档保留最近 8 个完成 ID。写入后读回失败、随后用同一 ID 重试时，若已落盘的 ID 仍在记录中，不再增加胜场或重新申报新纪录。它不影响独立钱包的实际到账；结算页可以同时显示“暖晶已到账”和“切磋纪录仍待保存”。该短期纪录去重窗口不是永久保留所有历史胜场 ID 的承诺。

习惯日记失败时明确提示本次习惯尚未存入日记、当前页仍可查看，不能把内存中的 `profile` 当作持久保存成功。战役和影子模式的 `recordRun` 使用 `recordOnly: true`，统计重试不会再次发放模式奖励。

若有尚未持久确认的路线、影子结果或习惯日记，第一次选择地图、工坊或退出等目的地会留在本页并提示重试或放弃；再次选择同一出口才离开。改选其他出口会重新要求两次相同选择。这个操作只放弃仍在内存中的未保存部分，不删除已保存的路线、待发队列或已到账暖晶。

已确认 `routeSaved: true` 的战役待发奖励本身可以在离开后补偿；若同局习惯日记仍未保存，日记仍属于需要上述放弃确认的内存部分。刷新页面、关闭标签页或进程退出无法自动恢复未曾落盘的完整结算输入；本轮没有增加战斗中途快照或影子结算持久队列。

## 未来版本保护与备份

Campaign 的 `getWriteProtection()` 对数值版本大于 `1` 返回 `future-save-version`，读取存储不可用时返回 `storage-unavailable`。通关入口、补偿入口和写入前都检查保护；默认路线视图不会授予覆盖未来存档的权限。Meta 同样保护顶层大于 `3` 或影子账本版本大于 `1` 的数据。结算页遇到未来版本保护时显示“新版存档已保护”，不把反复重试当作修复办法。合法旧版本迁移和原有坏 JSON 恢复行为继续保留。

[SaveBackupManager](../src/systems/SaveBackupManager.ts) 仍只处理固定的 8 个本游戏键，备份格式版本为 `1`，文件上限为 1 MiB。导出、预览和恢复使用领域校验，保留 Campaign 的有效 `pendingRewards`、Meta 的逐档已付账本，以及影子纪录中的有效完成 ID。未知未来领域版本或不支持的影子账本版本会拒绝导入，不通过净化把它伪装成可写的旧数据。

预览不写入，也不发奖励；确认恢复才写入并逐键读回，失败时尝试回滚并报告回滚是否完整。恢复成功回到菜单后，正常入口补偿流程处理备份中尚未完成的战役奖励。备份中的已付账本和凭据也同时恢复，避免把待确认奖励误当作新的首胜。备份不上传，不读取或覆盖其他 origin 键；它不是多设备同步或防回档防作弊系统。

## 已有分项验证与边界

本轮实际执行时，[Campaign 测试](../src/test/campaign.test.mjs) **24/24 通过**，[Backup 测试](../src/test/backup.test.mjs) **19/19 通过**。这些是当时的分项结果，不是最终发行测试总数。

Campaign 回归覆盖第 15 关钱包失败后跨刷新补发并解锁、第 3 关失败后正常继续下一关补偿、同凭据重复调用、路线写入静默拒绝、队列确认抛错或静默拒绝、超过最近 100 条窗口仍保留待发项、256 条容量拒绝不丢队列、旧 rc.2 可确认缺口补偿、旧已付结果不制造重玩奖励，以及未来版本不被覆盖。Backup 回归包含待发奖励和逐档账本往返、恢复后补偿一次、未知账本版本拒绝，并沿用坏数据、部分字段缺失和存储失败检查。

这些测试使用 Map 支持的存储替身及故障注入，验证的是实际管理器方法的状态和写入行为，不代表真实浏览器配额、跨标签页竞争或断电语义已经验收。本说明的结算 UI 部分来自当前调用关系核对，不把它计作图形或原生输入测试。最终完整检查、浏览器与图形证据统一查阅[发行准备与验收](release-readiness.md)。
