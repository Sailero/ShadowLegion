# 晒被沙原遮阳布原型：下一阶段实施审查

审查日期：2026-09-13。**本文是尚未实现的下一阶段方案，不代表沙原已经开放、完成验收或达到预计时长。** 本轮只新增本文档，没有修改源码、现有文档，也没有运行图形进程或构建。

依据为当前 [PostalWalkScene](../src/scenes/PostalWalkScene.ts)、[MountainScene](../src/scenes/MountainScene.ts)、[MountainRelay](../src/systems/MountainRelay.ts)、[旅程数据](../src/data/journey.ts)、[JourneyProgressManager](../src/systems/JourneyProgressManager.ts)，以及已有的[五地区实施计划](region-implementation-plan.md)、[故事与旅程](story-and-journey.md)和[三小时制作计划](steam-three-hour-plan.md)。较早文档中的“仅森林已实现”等描述是历史时间截面；当前实现与验收状态应以源码及对应版本 QA 记录为准。

## 1. 原型范围与核心操作

建议先实现“固定小暖一端、棉棉移动另一端”的遮阳布。三个谜题分别考查**方向、换锚绕石、同时覆盖**。难度来自真实位置、路线和重新分工，不增加展开倒计时、酷热掉血或强制等待。

收信人仍为仙人掌团刺。遮阴让卷叶展开，玩家读清门牌，再亲手投递岚角的信；门牌读清不等于已经交信。共同牵布表达的是彼此配合、找到双方舒服的距离。

原型只需要一块布、白名单锚点与路线、三个顺序目标和一个收信人。自由布料物理、绳索弹性、任意放置锚点、复杂自动寻路不在此阶段范围内。

## 2. 建议地图与三个空间谜题

建议世界为 **2400×1650**，出生点 `(230,1400)`，团刺小院约 `(2200,340)`。以下坐标是待实施布局，不是已有地图或已经完成通行测试的几何。

布面初始建议固定宽 `160px`，以两位角色的真实位置计算方向与展开长度；有效拉开范围暂取 `200–240px`。目标应有完整覆盖余量，例如目标半径 `16px` 加 `8px` 边缘余量，不只检查目标中心碰到阴影。四个朝向可以作为地面引导，但不得把棚端直接吸附到方向点、同时让角色仍站在别处。

| 谜题 | 空间与操作 | 实际完成条件 | 与上一项的区别 |
| --- | --- | --- | --- |
| ① 给卷叶一点阴凉 | 小暖锚点 `(500,1200)`；棉棉牵布后向东走到约 `(740,1200)`；卷叶门牌 `(690,1235)`。周围保留半径约290的无遮挡活动区。 | 两端实际牵住、布已拉开、门牌完整处于阴影内；棉棉在65px内按 F 读清。 | 教会“伙伴实际留守＋自己移动另一端”，空按 E 或走近门牌无效。 |
| ② 把阴凉搬到石堆另一边 | 石堆矩形约 `(1320,830,180,210)`；旧锚点 `(1270,980)` 不能有效覆盖目标。收布后绕到新锚点 `(1420,740)`；目标 `(1620,775)`，棉棉端约 `(1660,740)`。小暖的已知路线可经 `(1200,780)→(1300,700)→(1420,740)`。 | 小暖必须在新锚点实际到位；布面不能穿石堆。玩家应能提前看出旧锚点的覆盖范围不足，不强制先试错一次。 | 从转向增加到选择锚点、收布和绕障重新分工。路线要按人物体径与布面分别验证。 |
| ③ 留下两个人都舒服的位置 | 锚点 `(1750,500)`；棉棉端约 `(1990,500)`；门牌 `(1950,475)` 与软垫卷叶 `(1820,540)`。 | 两个目标必须在同一次有效布面状态下同时覆盖，再近距离 F 读门牌。不能先遮一个、松布后再遮另一个累计完成。 | 从单目标覆盖增加到同时满足两个空间条件，最后仍由玩家亲手确认地址。 |

上述正确姿态中，读牌点与棉棉的距离约为 `61px`、`53px`、`47px`，都小于建议的 `65px` 互动半径。这个算例只证明存在可用的目标姿态，不替代实际路径、碰撞和输入验收。

首个原型不要让遮阳布成为唯一可行走地面。软垫卷叶是需要遮阴的环境目标，不是松手后会消失的救命平台。读清门牌并确认保存后，将其记入邮袋，不因收布而遗忘；最终小院可出现固定遮阳棚作为可见变化。

## 3. 与现有行走和影伴契约的衔接

### 真实布面与扫掠

`PostalWalkScene.adjustWalkVelocity` 目前设置后续移动速度，不能证明此前物理步没有越过绳长边界或石堆。按当前轻跃速度 `470px/s` 与 `50ms` 帧步上限计算，单步位移可达约 `23.5px`。仅检查新位置合法，不能阻止布角或布面在两帧之间穿过障碍。

模型必须同时验证：

- 小暖已被指定到正确锚点，实际位于允许半径内，并保持留守。
- 棉棉实际牵住另一端，展开长度有效，两个端点都是有限且处于地图内的坐标。
- 阴影来自两端当前真实位置，目标完整位于有效布面内。
- 从上一合法姿态到当前姿态的移动与旋转没有扫过石堆。应检查整个矩形的扫掠，而不只是两端连线或最终四个角；采样间距须根据布角最大位移确定。
- 每次 F 读牌前刷新实际占位和覆盖，不能沿用上一帧已经失效的阴影结果。

### 超距、放下与召回

为先复用共享移动层，建议原型在超距或布面扫过障碍时**松布，并把布角留在最后合法落点**；玩家仍可步行回到布角旁 F 重牵。不得把玩家或小暖强拉到石堆内部，也不要让布角留在不可到达的地方。

这与旧实施计划中“到约束边界停住”的方案有所不同：若要保留硬性停住或沿边滑动，需要增加真实位置约束入口，并处理物理步、扫掠和恢复顺序，不能只套用现有风速钩子。

E 召回应先原子地释放两端、清除当前覆盖，再调用现有召回流程。复用 `sendEchoRoute` 的白名单路线，以及已走派遣路径反向返回；不能为换锚点直接修改小暖坐标。暂停只冻结当前姿态与模拟；失焦清除待执行输入，恢复后不能突然拖布。

## 4. 最小新增纯模型接口

以下接口仅为建议，尚未创建对应模块：

```ts
new PairedCover(confirmedCheckpoint)
assign(anchorId, player)                  // 返回白名单实际行走路线
grip(player)                             // 靠近当前合法布角，不能远距抓取
release()
update(delta, { player, echo, echoStays }) // 实际布面、碰石与松布事件
read(targetId, player)                   // 当前完整覆盖，产生一次成功事件
confirmSaved(puzzleId)
getSnapshot()
```

阶段可收敛为 `packed / awaitingEcho / ready / holding / laid / matchedPendingSave`。快照至少包含当前锚点、两端位置、阴影多边形、有效展开与阻挡原因、各目标当前覆盖、合法布角落点、已确认节点和待保存节点；快照与配置必须只读。

纯模型不移动角色、不操作存储、不交付信件。场景负责真实角色行动、绘制反馈与消费事件；模拟用有限帧步，暂停不调用推进，零时间更新只刷新空间状态。反复调用 assign、grip 或 read 不能积累完成次数。

F 的处理建议依次为：待保存重试、当前目标确认、明确提示的牵起或放下。一次 F 保存重试成功后立即返回，不能顺带做下一项动作。错误目标应给空间提示，不能意外把布收走；E 与 F 同帧时，召回后的 F 必须依据已经释放的状态重新判定。

## 5. 保存、恢复与备份版本边界

建议三个顺序节点为 `desert.coverLearned → desert.courtyardAligned → desert.addressRead`，名称待实施时统一。完成事件只发一次；保存失败保留 `matchedPendingSave`，让玩家原地 F 重试，不要求重做覆盖。

恢复只认已确认节点，重建在对应安全营地，布收好、小暖跟随。不得恢复拖拽坐标、半展开状态、未确认的匹配或中途派遣位置。最终投递继续使用独立且幂等的 completionId；保存拒绝和成功写入后读回失败的重试，都不能多发庆祝、凭据或回信。

当前 Journey 数据为 v3，沙原节点列表为空，也尚未解锁。下一阶段应一并处理这些边界：

1. **开放与前置同时落地。** 沙原只由山区真实投递凭据解锁；节点白名单、顺序校验、交付前置必须和地区开放一起增加。当前交付检查使用 `every`，空数组会通过，不能先开放沙原再补节点。
2. **明确旧版本的能力范围。** 如采用 v4，保留 v3 自己的节点和发现物白名单。旧 v3 不得携带后来才定义的沙原节点或凭据，并被新程序当作已经完成；迁移只保留原有真实进度。
3. **保留历史存储与未知数据保护。** 沿用现有 key 或新增 key 必须明确迁移路径，不因产品名、版本号或导入旧备份而丢失已有森林、湖泊和山区记录。未来版本、超长内容、非法 ID、读入口失败时拒绝覆盖。
4. **备份与运行时使用同一契约。** 导出、预览、恢复都要理解新节点和版本；恢复含沙原进度时验证山区凭据、三个节点顺序及唯一投递凭据。旧备份缺少新域时保留当前已有进度，不能静默清空。
5. **恢复失败可回滚。** 新版本备份的任何写入失败都应沿用现有回滚语义，包含写入成功后读回抛错的情况。不能通过清空原记录来让导入“成功”。

原型不增加另一套持久化“是否牵布”或“影伴坐标”字段，也不借用旧 Campaign 星章证明沙原已经完成。

## 6. 必须通过的软锁与操作边界

| 边界 | 必须成立的结果 |
| --- | --- |
| 小暖在路上、已被召回、未留守或站错锚点 | 无有效覆盖，不产生完成节点。 |
| 轻跃扫过石堆，但终点合法 | 仍不能穿布取巧；合法落布点可重新拿取。 |
| 任意拉布位置松手、召回、退出重进 | 玩家、布和小暖都有可达的继续路径；信不丢失。 |
| 两目标先后覆盖、边缘擦过、刚失去覆盖时按 F | 不得当成同次完整覆盖。 |
| 目标必须被遮住，同时要求近距离 F | 地图必须存在满足全部条件的实际站位，且鼠标和键盘都能走到。 |
| 同帧 E 召回与 F 读牌、快速连按、暂停前积压输入 | 只按当前有效状态处理；恢复后不重放旧牵引或互动。 |
| 匹配后的保存拒写、写成后读回失败、重复交信 | 可重试，不重复匹配反馈、交付凭据或庆祝。 |
| 布角掉落在窄口、障碍边或锚点另一侧 | 有明确且真实可走的重牵路径；不能要求先持布才能取得布。 |
| 静音、减少动态、失焦和阅读 | 仍可从图形判断两端、阻挡和覆盖；没有隐藏计时要求。 |

完成后还需以实际场景方法测试输入、移动、覆盖与保存的顺序，再做真实浏览器操作验收。纯几何或状态机测试不能独自证明拖拽手感、遮挡可读性和角色通行已经成立。

## 7. 时长目标与后续内容量

三个谜题、一次投递及回访可以作为 **8–12分钟原型的制作目标**，但实现这三项并不能证明玩家会玩够8分钟。本文没有进行沙原游玩测量，也不把路线长度、文本字数或自动更新时间转换为真人时长。

完整地区本轮讨论的是**约35分钟**目标，而旧五地区实施计划给沙原分配的是**40分钟**，两者尚待统一，之后还要重新汇总整条约三小时旅程。

若扩充完整地区，优先增加有新空间选择的复合庭院、可选择的住户路线，以及投递后发生变化、值得回看的小院。不要用增加相同卷叶数量、放慢行走或牵布、拖长展开过程、锁住对话阅读时间补足预算。

实际时长应在对应可玩版本完成后，记录首次玩家的探索、有效操作、尝试与求助、对话、可选路线、菜单及离开窗口时间，并报告样本差异。原型与完整地区的目标在获得这些证据前，都只能作为制作规划。
